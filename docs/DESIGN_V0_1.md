# 0.1.0 首版详细设计

状态：待用户确认，本文件不构成开始业务代码编写的授权。

本设计采用全新插件定位，只以人格、表达及 AstrBot 接入为首版目标。用户已确认项目名称和 Git 仓库；以下产品行为是本次提出的具体方案，确认后才成为实现基线。

## 1. 首版的用户体验

用户在 AstrBot 插件配置页完成以下操作：

1. 选择人格来源。
2. 填写角色与语言习惯，或者保留 AstrBot 已有角色。
3. 选择允许生效的私聊会话。
4. 保存配置、重载插件、启用。
5. 正常私聊，无需使用特殊聊天指令。

配置管理使用 AstrBot 自带界面。首版不另建网站、不要求模型 API Key、不要求修改 NapCat 连接。

首版支持一个活动角色配置，并可作用于多个明确选择的私聊会话；专属关系必须单独限定适用会话。多角色、多关系自动路由后续另行设计。

## 2. 人格来源：两种明确模式

| 模式 | 身份与性格来源 | 插件管理内容 | 运营者需要做什么 |
| --- | --- | --- | --- |
| plugin，推荐 | 插件内角色资料 | 角色、语言习惯、表达规则及可选关系资料 | 将目标 AstrBot 人格配置成不含重复角色身份的基础规则 |
| astrbot | 当前会话已有的 AstrBot 人格 | 语言习惯、表达规则、示例及可选关系资料 | 保持原有人格，不在插件中重复填写身份性格 |

- plugin 模式不会自动删除、修改 AstrBot 人格，也不会覆盖整个系统提示。
- 两处存在冲突时，不保证追加规则能够可靠解决冲突。配置说明要求只保留一个身份来源。
- astrbot 模式不通过私有接口读取人格数据库；沿用当前请求中 AstrBot 已组装的人格。
- 切换到 astrbot 模式后，已保存的角色资料保留但不注入，并在诊断中说明未使用。
- 两种模式都不改变模型、工具权限及宿主运行规则。
- 不提供普通聊天消息直接修改全局人格的命令。

## 3. 配置分组与默认行为

### 3.1 启用与作用范围

| 配置 | 建议默认值 | 行为 |
| --- | --- | --- |
| enabled | false | 新安装默认不注入，配置完成后启用 |
| persona_source | plugin | 选择上节两种模式 |
| allowed_sessions | 空列表 | 仅允许列表中精确匹配的私聊会话；空列表表示未配置，不匹配任何会话 |

allowed_sessions 保存 AstrBot 完整会话来源 UMO，可使用宿主选择器或手工填写。以宿主标识为准，不从昵称推断，不自行拼接或拆解 UMO。平台及私聊类型需同时匹配；即使填入群 UMO，也不允许群聊注入。

会话来源需要验证能够区分平台实例和机器人；如果目标 AstrBot 版本不能保证多机器人隔离，必须增加显式机器人约束后再支持该场景，不能假定同一用户 ID 等于同一会话。

### 3.2 角色资料：plugin 模式使用

| 配置 | 用途 | 空值规则 |
| --- | --- | --- |
| character.name | 角色称呼 | 必填 |
| character.identity | 身份、世界观和已确认背景 | 必填，避免插件自造身份 |
| character.personality | 性格、价值观、偏好、缺点和反应倾向 | 必填，建议写具体行为 |
| character.boundaries | 角色立场、拒绝方式和相处边界 | 可选，不填写不新增 |

各字段用自由文本描述，不要求 MBTI 或人格数值。关系中的用户事实不能写进通用角色资料。

示例仅说明填写方式，不作为默认角色：

> 平时说话简短，熟悉后会轻轻吐槽。认真讨论时愿意展开，不会因为对方不赞同就立刻改口。不擅长说很煽情的话，关心别人时先回应眼前发生的事。

### 3.3 关系资料：两种模式都可使用

| 配置 | 默认值 | 行为 |
| --- | --- | --- |
| relationship.target_session | 空字符串 | 明确关系归属的一个完整私聊 UMO，且必须属于 allowed_sessions |
| relationship.background | 空文本 | 关系背景、已确认的共同经历和相处阶段 |
| relationship.addressing | 空文本 | 双方称呼和使用场景 |

- 关系资料与称呼均为空时，不生成任何关系提示。
- 填了关系资料却未选择目标会话，属于无效配置。
- 只对目标会话注入关系资料；同一角色服务其他允许会话时，不带入该关系。
- 不默认恋人、朋友、年龄、性别或亲密程度。
- 首版只提供一个专属关系条目，多关系列表不是本次隐含范围。

### 3.4 表达设置

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| expression.habits | 空文本 | 固定表达习惯，例如认真时少用语气词 |
| expression.tone | follow_character | follow_character / gentle / playful / reserved，角色基础上可选的语气偏好 |
| expression.length | adaptive | adaptive / brief / expanded；只影响闲聊倾向，不能硬截断正文 |
| expression.actions | none | none / occasional / scene；分别为直接聊天、少量动作、场景扮演 |
| expression.emoji | occasional | none / occasional / frequent；仍以角色、话题和用户当轮要求为依据 |
| expression.reduce_cliches | true | 减少无关总结、逐句复述、固定安慰与每轮追问 |
| expression.extra | 空文本 | 少量补充要求，不用于另写一套冲突的人格 |

具体期望：

- 认真求助时可以分析和给步骤；吐槽时不自动切成建议清单。
- 不强制每次提问、叫昵称或声明陪伴。
- 有分歧时保持立场，并针对具体内容表达。
- 依靠已有上下文延续态度；用户换话题时跟随，不反复纠缠。
- 场景模式不得替用户决定动作和心理；未知现实行为不得编造成已完成事实。
- 语气只是偏好，不保证模型逐字遵从，须通过试聊评估。

### 3.5 对话示例

examples 使用多行文本，以“情境 / 用户 / 角色”的方式填写，建议 3～8 组。示例的作用仅是展示说话方式。

- 示例不会追加为真实历史消息，不写入任何记忆。
- 示例中的名字、经历、亲密关系不授予角色新的事实。
- 示例不具备真实工具调用资格，不能作为已执行动作的证据。
- 若示例明显与角色资料矛盾，应修改配置；首版不额外调用模型自动审稿。

## 4. 规则如何组成

| 层 | 资料 | 放置方式 |
| --- | --- | --- |
| 宿主基础 | AstrBot 人格基础、工具和必要规则 | 保持原始内容 |
| 插件稳定部分 | 所选来源的人格、表达习惯及示例 | 独立可识别的系统提示区块 |
| 会话专属部分 | 已人工配置的关系与称呼 | 仅目标会话使用的独立区块，固定配置在同一会话内保持稳定 |
| 当前上下文 | 用户输入、聊天历史、附件、工具结果 | 保留 AstrBot 正常处理 |

首版不生成每轮动态心情、好感度或时间提示，不为“像人”额外进行一次改写调用。

优先关系：宿主必要规则必须保留；角色事实由明确配置来源决定；当前用户提出的长度、格式和话题要求可以调整本轮表达。语言习惯不是改变角色事实或工具结果的依据。

自有区块可替换，重复钩子或重试不得反复堆叠；不按宽泛正则删除其他插件或宿主内容。

## 5. 配置校验与错误行为

- enabled、列表、枚举、嵌套字段均做类型校验，不把错误字符串自动解释为全部会话。
- plugin 模式缺少必填角色资料时不生效；astrbot 模式允许这些字段为空。
- 配置错误时，本轮跳过插件注入，让 AstrBot 按正常流程运行；不阻断用户聊天，不改用一个临时人设。
- 关系目标不在允许列表时不生效，并提示具体字段错误。
- 总文本预算建议为 12,000 个 Unicode 字符，包含角色、关系、表达与示例的用户填写文本；这是实现上限建议，不是 token 或费用承诺。
- 超过上限拒绝采用配置，不静默截断角色或示例；提示减少重复规则。
- 保留区块标记须转义，避免运营者粘贴内容破坏区块替换。
- 每次请求使用一个配置快照；即使保存操作发生在请求中途，也不混用半份旧配置和半份新配置。
- 保存并重载是首版明确支持的生效方式；无重载即时生效仅在目标宿主验证后再声明。

## 6. 管理与诊断

首版提供一个管理员可用的只读状态入口，建议命令为 `/人格状态`，最终名称在检查冲突后确定。

显示：插件版本、启用状态、人格来源、配置有效性、本会话是否命中、最近一次注入结果和原因代码。

- 不在聊天中展示完整人设、示例、其他会话 ID 或原始用户消息。
- 非管理员无法通过状态入口读取运营配置。
- 状态只表示插件规则是否加入请求，不声称模型已经遵从或 QQ 已送达。
- 诊断运行状态仅存在内存中，重载后可重置；首版不引入专用数据库。
- 管理指令使用宿主命令处理，不额外调用模型生成答复。

## 7. 首版明确不承诺的能力

持久情绪、长期记忆、自动学习、多角色切换、主动联系、生活日程、分段发送和语音生图不纳入 0.1.0 实现基线。AstrBot 自身已有的历史、工具和模型能力可正常使用，兼容效果需实测。

## 8. 实施顺序与待确认点

1. 用户确认本设计的产品行为。
2. 根据宿主版本核实接口，配置工具链，建立最小插件骨架。
3. 跑通私聊作用域与只读状态，不先写全部人格功能。
4. 实现配置校验和稳定规则组装，补齐关键逻辑测试。
5. 集成到实际 AstrBot 环境，按验收文档试聊。
6. 形成 0.1.0 安装包及验证记录。

本轮最需要确认的是：首版先完成上述人格表达闭环；人格来源采用 plugin 或 astrbot；单角色和单条专属关系是否适合第一阶段。实际角色资料可在配置功能完成后填写，不阻塞工程设计。

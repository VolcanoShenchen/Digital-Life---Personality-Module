## 5. 人格与表达设计

人格资料采用可解释的结构：

- 身份事实：角色是谁，已确认的背景与关系。
- 性格与立场：在关心、分歧、压力、玩笑等情境中的反应倾向。
- 语言习惯：常用措辞、句式、语气词、亲昵称呼和旁白偏好。
- 对话示例：示范节奏、表达和回应重点，不能作为真实经历写入记忆。
- 表达边界：角色不愿做什么、如何拒绝、如何表达不同意见。

回复长度随内容变化；普通闲聊可简短，解释、代码和认真求助需要完整。不得通过机械截短、随机错字或固定动作模板代替表达设计。

首版的情绪与话题承接依靠 AstrBot 已提供的上下文。是否建立跨会话持久状态，应在后续模块中明确，不提前承诺持久情绪能力。

## 6. 与 AstrBot 的对接方案

### 主流程

消息事件 → 判断是否适用 → 读取角色与表达配置 → 通过官方请求扩展机制补充规则 → AstrBot 生成并发送 → 按实际成功情况更新诊断。

### 对接原则

- 普通聊天沿用单一生成和发送流程，避免重复调用与重复回复。
- 新插件配置作为角色资料主来源；AstrBot 原生人格与其明确分工，避免重复定义身份和性格。
- 保留 AstrBot 必要的系统规则与工具说明，不覆盖整个系统提示。
- 稳定人格与动态信息分开处理，避免每轮改写稳定人格破坏提示词缓存。
- 重试或重复钩子调用不得不断累加同一份规则。
- 配置错误有明确诊断，不默默扩大用户适用范围。
- 配置与诊断不得默认记录完整私聊内容。

### 实现前及集成时核对

- 用户实际运行的 AstrBot 版本与 Agent 执行方式。
- 私聊、真实发送者、机器人和平台实例的标识接口。
- 请求钩子顺序与配置生效方式。
- 流式与非流式回复、工具调用和多模态附件。
- 发送结果、聊天历史落库和插件状态更新的先后关系。
- 数据目录、热重载、退出清理与并发消息处理。

兼容版本应在核实与验证后写入元数据，不能直接继承已有草稿的版本声明。

## 8. 建议项目结构

以下为规划，不提前创建所有目录；以实际模块规模逐步建立。

```text
General_purpose_personality_plugin/
  main.py                  # AstrBot 入口与生命周期
  metadata.yaml            # 插件识别、版本与兼容范围
  _conf_schema.json        # 配置面板
  README.md                # 安装、配置、使用与限制
  CHANGELOG.md
  pyproject.toml           # 开发检查与项目约定
  requirements.txt         # 运行依赖
  .gitignore
  .gitattributes
  docs/
    PLAN.md                # 确认后的开发计划
    ARCHITECTURE.md         # 模块职责与 AstrBot 对接
    ACCEPTANCE.md           # 验收场景与结果
  core/
    persona.py             # 角色与关系配置
    expression.py          # 表达规则组装
  integrations/
    astrbot_adapter.py     # 宿主适配，视规模决定是否拆分
  tests/
  scripts/                 # 打包和发行包检查
```

如果首版确有持久化需求，再增加 storage 模块。状态和长期记忆功能被确认后再增加对应模块，避免预先建立空架构。

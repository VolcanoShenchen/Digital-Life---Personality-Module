# 首版 AstrBot 对接架构

状态：已按确认方案实现，开发接口基线为 AstrBot v4.29.4（提交 61335414433db721b3f7ecc93f90deafe0a59d78）、Python 3.12+、内置 Agent。源码核对与本地测试不等于云端集成通过；见 [验证记录](VALIDATION.md)。

## 1. 官方依据与验证边界

本次核对了 AstrBot 官方文档：

- [消息事件与请求钩子](https://docs.astrbot.app/dev/star/guides/listen-message-event.html)：`on_llm_request` 可获取 `ProviderRequest`；事件钩子不能与消息过滤装饰器叠加，作用域需在钩子内检查。
- [插件配置](https://docs.astrbot.app/dev/star/guides/plugin-config.html)：通过插件配置 Schema 定义设置，由 AstrBot 提供管理界面、持久化及配置对象。
- [插件开发入口](https://docs.astrbot.app/dev/star/plugin-new.html)：插件入口、元数据、兼容版本、重载与依赖管理。

官方文档确认稳定角色规则适合放入系统提示；每轮变化的状态不宜放入稳定系统提示。文档也给出动态附加内容机制，作为未来扩展的候选接口，本次不实现动态状态。

当前未知：用户实际 AstrBot 版本、Python 版本、Agent 执行器、是否启用流式回复、模型提供商及多机器人会话设置。未知项不会被写成已支持声明。

## 2. 最小模块划分

| 模块 | 责任 | 不承担的工作 |
| --- | --- | --- |
| 插件入口 | 生命周期、请求钩子、管理员状态命令 | 不手动重发普通聊天 |
| 配置解析 | 类型、必填、作用域、文本预算校验；生成不可变快照 | 不猜测缺失的角色事实 |
| 人格与表达 | 生成选定来源的稳定区块，按会话决定关系区块 | 不读取 QQ 原始协议，不调用模型 |
| 请求适配 | 保留原系统提示，替换自有区块，记录注入结果 | 不覆盖历史、工具和多模态内容 |
| 运行诊断 | 记录有限的状态与原因代码 | 不保存完整聊天、人设或其他用户资料 |

首版按规模采用少量 Python 模块，不要求为每个概念建立包。实际文件布局在工具链阶段确定。

## 3. 请求生命周期

1. AstrBot 按正常规则判断消息是否触发模型。
2. 插件在官方请求钩子中获取事件与待发送模型的请求。
3. 读取本轮一致的配置快照。
4. 校验平台与私聊类型，精确匹配允许会话。
5. 根据人格来源构建稳定规则，仅命中关系目标时构建关系规则。
6. 在原系统提示中仅替换本插件自有区块。
7. AstrBot 继续执行模型、工具、流式与发送流程。
8. 插件诊断记录“已注入”或“已跳过”，不将其当作送达证明。

插件不通过全消息监听自行触发第二次模型请求，不在模型响应后进行第二次模型润色，不干预普通回复发送。

宿主可能有工具循环和失败重试，因此验收比较插件启用/关闭的基线：要求插件不新增模型调用或重复发送，不能把宿主一次触发必定只调用模型一次当作前提。

## 4. 人格与宿主共存

plugin 模式下，插件是角色身份的配置来源，但没有权限识别并任意删除原系统提示中的角色文字。安装说明要求运营者先整理对应 AstrBot 人格，保留必要基础规则，清除重复身份。

astrbot 模式只沿用已组装的宿主人格，不加载宿主私有人格存储，也不自动更改 AstrBot 的人格选择。

两个模式均保留工具说明、用户输入、会话历史、附件和工具结果。插件自己的区块应有明确命名与版本标记，移除逻辑只匹配完整自有区块。

不宣称可以与任意其他人设重写插件自动协调；集成时检查当前请求是否有后执行的改写，必要时明确不支持该组合，而不是反复争夺最后一次写入。

## 5. 作用域与关系归属

- 以 AstrBot 官方完整会话标识进行匹配，同时检查平台、私聊类型及 allowed_bot_ids 中的机器人自身账号。
- allowed_sessions 或 allowed_bot_ids 任一为空时不注入。
- 专属关系同时绑定完整私聊来源与机器人 self_id，不能仅凭昵称、用户 ID 或 UMO 注入。
- 角色规则可服务多个允许会话；不同会话不共用动态诊断对象。
- 首版不创建长期状态，减少状态串用；内存诊断也需按实际会话隔离并设容量上限。

## 6. 重试、停用与异常

| 场景 | 预期行为 |
| --- | --- |
| 同一请求重复进入钩子 | 自有区块数量保持稳定，不重复追加 |
| 配置更新后重载 | 新请求使用完整新配置 |
| 重用请求但当前不适用 | 清除可确认属于插件的自有区块，保留其他内容 |
| 配置无效或超过预算 | 跳过注入，记录固定字段与错误码，不打印原始文本 |
| 请求结构不受支持 | 跳过注入并给出诊断，不把附件或工具转换成纯文本 |
| 局部插件异常 | 尽可能保持原请求，隔离插件错误；不吞掉任务取消和宿主终止信号 |
| 插件卸载/停用 | 释放内存对象和注册资源，不改写宿主历史 |

写请求应尽量最后一步完成；在完整规则构建成功前，不对原请求做部分修改。不得用正则删除历史中的角色回复来模拟清理。

日志按原因码记录配置无效、范围不匹配、结构不支持及注入完成；重复错误做有限去重。用户输入不能作为格式字符串或完整日志消息使用。

## 7. 持久化与缓存

- 运营配置由 AstrBot 插件配置机制保存。
- 首版不另外创建记忆库或角色数据库，不保存聊天副本。
- 稳定规则可按有效配置修订缓存，缓存不得包含用户输入。
- 不承诺特定服务商的缓存命中率或费用下降；只能保证插件不主动加入时间戳等无必要变化。
- 状态命令展示的最近结果保存在有限内存缓存中，重载重置。

## 8. 工程工具链建议

- 使用 Python 标准库实现首版核心逻辑，运行时依赖 AstrBot 提供的 API。
- 开发检查建议 Ruff，测试建议标准库 unittest；不为格式检查安装整个模型或 QQ 运行栈。
- 开发依赖与运行依赖分开声明，检查版本在实施时选定并固定。
- Python 最低版本从所选 AstrBot 测试版本核实，不能根据本机解释器直接决定。
- 首次插件元数据需确认内部标识符合 AstrBot 加载规范；项目名称、仓库名称和内部标识可以不同，内部标识不静默重命名项目。
- 集成阶段使用可记录的宿主版本或提交，避免仅依赖随时变化的上游主分支。
- 安装包使用显式文件清单，排除 Git 元数据、开发缓存、运行配置和聊天资料。
